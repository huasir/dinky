# Dinky 公司二次开发：版本与分支管理

> 适用场景：基于官方 Dinky 发行版做定制开发、发布生产，并需随时对齐官方某一版本。  
> 文档位置：`docs-ltsk/`（公司内部文档，不进入官方 `docs/`，降低跟官方合并时的冲突面）。

## 1. 目标

- 始终基于**官方某个稳定发行线**做迭代，而不是直接在官方 `dev` 上堆业务。
- 生产发布可追溯、可回滚（以 tag 为准）。
- 可随时将定制代码升级到官方更新的版本（如 `1.2.4` → `1.2.5`）。
- 三远程职责清晰，避免误推官方仓。

## 2. Remote 角色

| Remote     | 地址（示例）                                   | 用途                         | 推送策略                |
|------------|------------------------------------------------|------------------------------|-------------------------|
| `upstream` | `https://github.com/DataLinkDC/dinky.git`      | 官方源，只读对齐             | **禁止 push**           |
| `origin`   | `git@github.com:huasir/dinky.git`              | 个人备份、实验、PR 草稿      | 可 push 任意分支        |
| `ltsk`     | `http://10.0.0.68/big-data-dev/dinky4.git`     | 公司正式仓、发版与生产依据   | **只推约定分支与 tag**  |

建议禁用 upstream 的 push URL：

```bash
git remote set-url --push upstream DISABLE
```

日常同步官方：

```bash
git fetch upstream --tags
git fetch ltsk
git fetch origin
```

## 3. 分支模型

### 3.1 总览

```
upstream/1.2.4  (官方 release 线 / tag v1.2.4)
        │
        ▼
   vendor/1.2.4          ← 公司主开发线（定制 commit 落在这里）
        │
   ┌────┼────────────┐
   │    │            │
feature/*  hotfix/*  upgrade/1.2.4→1.2.5
                     │
                     ▼
                vendor/1.2.5     ← 对齐官方新版本后的新主线
                     │
                     ▼
              tag: ltsk-1.2.5.0  → 推 ltsk，用于生产
```

### 3.2 长期分支

| 分支             | 含义                                       | 推送到          |
|------------------|--------------------------------------------|-----------------|
| `vendor/<x.y.z>` | 基于官方 `<x.y.z>` 的公司主线              | `ltsk`、`origin` |
| `prod`（可选）   | 指向当前生产正在运行的 commit；也可用纯 tag | 仅 `ltsk`       |

命名约定：

- 使用 `vendor/1.2.4`，**不要**使用与官方 tag 易混淆的本地分支名（如 `v1.2.4`）。
- 每个对齐的官方小版本对应一条 `vendor` 线；升级官方版本时开**新** `vendor` 线，而不是在同一条线上无限堆叠。

### 3.3 短期分支

| 分支                     | 用途                                         |
|--------------------------|----------------------------------------------|
| `feature/<topic>`        | 从当前 `vendor/x.y.z` 拉出，合回同一 vendor 线 |
| `hotfix/<topic>`         | 从生产 tag / `prod` 拉出，紧急修复           |
| `upgrade/<from>→<to>`    | 官方版本升级专用工作分支                     |

### 3.4 明确禁止

- 在 `upstream/dev` 或长期跟踪官方 `dev` 的分支上直接堆公司业务代码。
- 把公司定制 push 到与官方同名的分支（如 `1.2.4`）并当作生产基线。
- 用单一 `main` 承载所有官方版本线（升级时历史难追溯）。
- 向 `upstream` push。

## 4. 版本号与 Tag

官方已有 `v1.2.4`、`v1.2.5` 等 tag。公司发版使用**第四段 + 前缀**，避免与官方 tag 冲突：

```
ltsk-<官方版本>.<公司修订>

示例：
  ltsk-1.2.4.1   # 基于官方 1.2.4 的第一版生产
  ltsk-1.2.4.2   # 同基线小迭代 / hotfix
  ltsk-1.2.5.0   # 完成升级到官方 1.2.5 后的首发
```

语义：

| 部分       | 含义                                       |
|------------|--------------------------------------------|
| 前三段     | 对齐的官方 release 版本                    |
| 第四段     | 公司在该官方基线上的迭代序号               |
| 升级官方后 | 第四段从 `.0` 重新计数                     |

**纪律：生产部署、发布说明、回滚一律以 `ltsk-*` tag 为准，不以分支 tip 为准。**

## 5. 日常开发流程

```bash
# 1. 同步远程
git fetch upstream --tags
git fetch ltsk
git fetch origin

# 2. 从公司主线开功能分支
git checkout vendor/1.2.4
git pull ltsk vendor/1.2.4
git checkout -b feature/xxx

# 3. 开发、自测后合回 vendor/1.2.4（建议走 MR/PR）
git checkout vendor/1.2.4
git merge --no-ff feature/xxx
git push ltsk vendor/1.2.4
git push origin vendor/1.2.4
```

### 5.1 发布生产

```bash
git checkout vendor/1.2.4
git pull ltsk vendor/1.2.4

# 打 annotated tag
git tag -a ltsk-1.2.4.1 -m "生产发布：说明本次包含的能力/修复"
git push ltsk vendor/1.2.4
git push ltsk ltsk-1.2.4.1

# 可选：备份到个人仓
git push origin vendor/1.2.4
git push origin ltsk-1.2.4.1
```

生产环境只检出 tag：

```bash
git fetch ltsk --tags
git checkout ltsk-1.2.4.1
```

## 6. 跟官方升级（核心流程）

目标：从「基于官方 A 的定制」升级到「基于官方 B 的定制」，并保留公司 patch。

### 6.1 推荐：新 vendor 线 + merge（可追溯）

以 `1.2.4` → `1.2.5` 为例：

```bash
git fetch upstream --tags

# 1. 用官方 1.2.5 开新公司主线
git checkout -b vendor/1.2.5 v1.2.5
# 或：git checkout -b vendor/1.2.5 upstream/1.2.5

# 2. 把旧定制合进来
git merge vendor/1.2.4
# 解决冲突：优先保留官方安全修复，再重放公司逻辑

# 3. 验证（编译、启动、CDC、MCP、权限、关键回归等）

# 4. 推送并首发
git push -u ltsk vendor/1.2.5
git push -u origin vendor/1.2.5
git tag -a ltsk-1.2.5.0 -m "对齐官方 1.2.5 首发"
git push ltsk ltsk-1.2.5.0
```

升级完成后：

- 新开发切到 `vendor/1.2.5`。
- 旧线 `vendor/1.2.4` 保留一段时间，便于回滚与对照。

### 6.2 可选：rebase（历史更干净）

适用条件：

- 公司定制 commit 较少；
- 希望历史呈现「官方基线 + 干净补丁序列」；
- **尚未**被多人长期依赖的共享分支，或不对已推送的共享 `vendor/*` 强推。

建议在独立升级分支上试验：

```bash
git checkout -b upgrade/1.2.4→1.2.5 vendor/1.2.4
git rebase v1.2.5
# 解决冲突并验证后，再创建/更新 vendor/1.2.5
```

### 6.3 升级检查清单

1. 列出官方变更：`git log v1.2.4..v1.2.5 --oneline`
2. 列出公司定制：`git log v1.2.4..vendor/1.2.4 --oneline`
3. 冲突处理原则：官方安全修复优先，公司业务逻辑手工重放
4. 全量验证：编译打包、启动、作业提交、Vastbase CDC、MCP、权限等
5. 打 `ltsk-1.2.5.0` 并推 `ltsk`
6. 生产切换；旧 tag / 旧 vendor 线保留作回滚窗口

## 7. Hotfix 流程

```bash
# 从当前生产 tag 拉出
git checkout -b hotfix/xxx ltsk-1.2.4.1
# ... 修复并验证 ...

# 合回当前公司主线
git checkout vendor/1.2.4
git merge --no-ff hotfix/xxx
git tag -a ltsk-1.2.4.2 -m "hotfix: 简述"
git push ltsk vendor/1.2.4 ltsk-1.2.4.2

# 若已存在更新的 vendor 线，同步 cherry-pick
git checkout vendor/1.2.5
git cherry-pick <hotfix-commit>
```

## 8. Commit 分层建议

定制改动尽量按主题拆分，降低升级冲突成本：

1. **适配层**：Vastbase、驱动、配置差异（最易冲突，单独 commit）
2. **功能增强**：如 MCP Server（相对独立）
3. **工程杂项**：`.gitignore`、本地 IDE 配置（勿与业务混在同一 commit）

新功能保持小步、单一主题，便于升级时 cherry-pick 或定位冲突。

## 9. 当前仓库落地对照

| 现状 | 建议动作 |
|------|----------|
| 本地分支名 `v1.2.4`，跟踪 `upstream/1.2.4`，领先若干定制 commit | 重命名为 `vendor/1.2.4`，改跟踪 `ltsk` / `origin` |
| 尚无公司发版 tag | 稳定后打 `ltsk-1.2.4.1` 并推 `ltsk` |
| 官方已发布 `v1.2.5` | 按第 6 节建立 `vendor/1.2.5`，不要在旧线上硬合官方 tip 当生产 |
| 存在 `origin/dev` | 可作个人实验；公司交付只认 `vendor/*` + `ltsk-*` |

一次性重命名示例（需确认无他人依赖旧分支名后再执行）：

```bash
git branch -m v1.2.4 vendor/1.2.4
git push -u origin vendor/1.2.4
git push -u ltsk vendor/1.2.4
# 确认无误后，再删除远程旧分支名（如有）
```

## 10. 一句话纪律

**开发看 `vendor/<官方版本>`，生产看 `ltsk-*` tag，升级开新 `vendor` 线再合定制，官方仓只 fetch 不 push。**
